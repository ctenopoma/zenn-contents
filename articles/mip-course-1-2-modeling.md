## 悪い例:数式の書き写し

前回のノリで書くとこうなります。

```python
m.addCons(234*gohan + 149*pan + 108*tori + 71*tamago + 122*gyunyu
          + 14*horenso + 84*natto + 86*banana >= 2000)   # エネルギー
m.addCons(4.0*gohan + 5.6*pan + 22.0*tori + ...)          # たんぱく質(以下略)
```

これは**書いた瞬間から負債**です。食品が1つ増えたら全制約を書き直し。係数の転記ミスは見つけようがない。実務でこの書き方をしてはいけません。

## 良い例:データと定式化を分離する

定式化を組み立て直します。ポイントは「**データを辞書に、構造をループに**」。

### ステップ1:データを辞書にする

```python
foods = {
    "ごはん(150g)":    {"cost": 50,  "max": 6},
    "食パン(60g)":     {"cost": 40,  "max": 6},
    "鶏むね肉(100g)":  {"cost": 120, "max": 4},
    "卵(50g)":         {"cost": 30,  "max": 4},
    "牛乳(200ml)":     {"cost": 60,  "max": 4},
    "ほうれん草(80g)": {"cost": 70,  "max": 4},
    "納豆(45g)":       {"cost": 40,  "max": 3},
    "バナナ(100g)":    {"cost": 40,  "max": 4},
}
nutr = {  # 食品ごとの栄養素含有量(表をそのまま辞書化)
    "ごはん(150g)": {"エネルギー": 234, "たんぱく質": 4.0, "カルシウム": 5, "鉄": 0.2, "ビタミンC": 0},
    # ...(以下、表のとおり)
}
req = {"エネルギー": 2000, "たんぱく質": 60, "カルシウム": 650, "鉄": 7.5, "ビタミンC": 100}
```

実務ではこの部分が `pd.read_csv(...)` になります。**データの出どころが変わっても、以降の定式化コードは1文字も変わらない**のが分離の効能です。

### ステップ2:変数・制約・目的関数をループで組み立てる

```python
from pyscipopt import Model, quicksum

m = Model("diet")

# 変数: 食品ごとの摂取量(連続変数、0〜上限)
x = {f: m.addVar(name=f, ub=foods[f]["max"]) for f in foods}

# 制約: 栄養素ごとに「含有量の合計 >= 必要量」
for n in req:
    m.addCons(quicksum(nutr[f][n] * x[f] for f in foods) >= req[n], name=n)

# 目的関数: 食費の合計を最小化
m.setObjective(quicksum(foods[f]["cost"] * x[f] for f in foods), "minimize")

m.optimize()
```

定式化の本体は**10行**です。食品が800種類になってもこの10行のままです。

数式で書けば、やっていることはこうです。

$$\min \sum_{f} c_f x_f \quad \text{s.t.} \quad \sum_{f} a_{fn} x_f \ge r_n \ \ (\forall n), \quad 0 \le x_f \le u_f$$

「食品の集合 $f$」「栄養素の集合 $n$」を添字にした一般形。**数式の $\sum_f$ がコードの `quicksum(... for f in foods)` に1対1対応**しています。この対応が読めるようになると、論文や教科書の定式化をそのままコードに落とせるようになります。

### PySCIPOptの文法メモ

| やりたいこと | 書き方 |
| ---- | ---- |
| 連続変数(デフォルト、下限0) | `m.addVar(name="x")` |
| 上下限つき | `m.addVar(lb=1, ub=6)` |
| 整数変数 / 0-1変数 | `m.addVar(vtype="I")` / `m.addVar(vtype="B")` |
| 総和 | `quicksum(係数 * x[i] for i in 集合)` |
| 制約に名前をつける | `m.addCons(式, name="エネルギー")` |
| 最小化 / 最大化 | `m.setObjective(式, "minimize" / "maximize")` |
| 解の取り出し | `m.getVal(x[i])`(必ず `getStatus()` の確認とセットで) |

:::message
総和にはPython組み込みの `sum` ではなく `quicksum` を使ってください。結果は同じですが、`quicksum` は式オブジェクトの構築が一括で行われるため、変数が多いときの**モデル構築時間**が大きく違います。
:::

## 検算の道具:writeProblem

「コードは書けたが、意図どおりの数式になっているか?」を確かめる道具が `writeProblem` です。

```python
m.writeProblem("diet.cip")
```

SCIPが内部に持っているモデルがテキストで出力されます(抜粋)。

```text
  [linear] <エネルギー>:  +234<ごはん(150g)> +149<食パン(60g)> +108<鶏むね肉(100g)>
           +71<卵(50g)> +122<牛乳(200ml)> +14<ほうれん草(80g)> +84<納豆(45g)>
           +86<バナナ(100g)> >= 2000;
```

**転記ミス・符号ミス・抜けは、このファイルを見れば一発でわかります。** 定式化のデバッグでまず最初にやることです。制約に名前(`name=n`)をつけたのはこのためでもあります。

もうひとつの検算が、制約行列そのものの可視化です。行=栄養素、列=食品で「1単位あたり必要量の何%を賄えるか」をヒートマップにしました。

![制約行列](/images/mip-course-1-2-modeling/fig1_matrix.png)

「たんぱく質は鶏むね、カルシウムは牛乳、ビタミンCはほうれん草が担当」という**データの構造**が定式化前に見えます。もしこの図で1行まるごとゼロ(どの食品でも賄えない栄養素)があれば、解く前に実行不能だとわかります。

## モデルの答えは「書いたことしか」守らない

ところで、この献立を実際に食べたいでしょうか。ごはん5杯、バナナ4本、肉なし。栄養的には正しくても、献立としては誰も食べたくない代物です。

これはソルバーのバグではありません。**「おいしさ」や「食事らしさ」を制約にも目的関数にも書いていない**のだから、モデルがそれを考慮しないのは当然です。実務の最適化で一番多い失敗は、解けないことではなく「**現場が守っている暗黙のルールをモデルに書き忘れて、正しく変な解が出る**」ことです。

変な解が出たら、それは**現場の要件を聞き出すチャンス**です。「この献立のどこが駄目ですか?」→「肉が無いのはありえない」→ 制約に追加。このループの回し方は第6部(6-4)で扱います。

## まとめ

- データは辞書(実務ではCSV)、定式化はループ。**数式の書き写しは負債**
- 数式の $\sum_f$ とコードの `quicksum(... for f in foods)` は1対1対応
- 検算は `writeProblem` と制約行列の可視化。デバッグは解く前から始まる
- 変な解はバグではなく「書いていない要件」の発見器
