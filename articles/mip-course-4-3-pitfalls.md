## 事故の再現:規模とともに開く「定式化のハサミ」

2-4の施設配置問題を、規模を変えて弱い定式化(集約Big-M)と強い定式化(個別リンク)で解き比べました。

![スケーリング](/images/mip-course-4-3-pitfalls/fig1_scaling.png)

| 規模(施設F×顧客3F) | 弱い定式化 | 強い定式化 |
| ---- | ---- | ---- |
| F=15 | 0.1秒 | 0.0秒 |
| F=30 | 5.2秒 | 0.1秒 |
| F=60 | 9.3秒 | **0.4秒**(23倍差) |

事故の構造が見えます。**F=15(テストデータ規模)では両者とも一瞬で、定式化の弱さは完全に不可視**です。差は規模とともに開き、本番規模で顕在化する。「手元では解けた」は、モデルの健全性を何も保証していなかったのです。

対策はシンプルで、第4部でやってきたことそのものです。

- 小規模でも**LPギャップを測る**(4-1)。ギャップは規模に関係なく定式化の弱さを暴く。弱い定式化はF=15の時点でギャップ46%でした
- **規模のスケーリングテスト**を開発項目に入れる。テスト→本番で問題サイズが10倍になるなら、5倍サイズで一度は解いておく

## presolve:ソルバーの中の掃除人

2-3のログの冒頭に流れていた presolve の仕事を確認します。3-2のシフトモデルで前処理前後の問題サイズを比べると:

```python
m.presolve()   # 求解せず前処理だけ実行できる
```

```text
元の問題:      変数 184, 制約 152
presolve後:    変数 150, 制約 108
```

変数34個と制約44本が消えました。消えたのは主に**希望休で0に固定された変数**とその連鎖(固定変数を含む制約の簡約)です。人間が「安藤さんの金曜は考えなくていい」と分かるのと同じ推論を、presolveが機械的にやっています。他にも:

- **限界の引き締め**: $x \ge 40$ と $x \le 10^{12} y$ から「$y=1$ しかない」を導いて固定(実測: この2制約だけの問題はpresolveだけで解き切られ、探索ノード0で終了しました)
- **制約の格上げ**: 一般線形制約を knapsack や setcover などの構造つき制約へ変換(2-3で見た `15 upgd conss`)。専用のカットやヒューリスティクスが解禁される
- **支配・重複の削除**、係数の強化(実はこれ、4-2でやったカットの親戚です)

ひとつ正直な実測報告を。今回いくつかのモデルでpresolveをオフにして比べましたが、**きれいに書かれたモデルでは速度差がほぼ出ません**でした(ビンパッキングで7.5秒 vs 6.9秒など)。presolveが劇的に効くのは、冗長・スロッピーなモデルや、固定変数だらけのデータが来たときです。つまり「presolveがあるから雑に書いてよい」ではなく、**presolveは保険**と考えるのが正しい姿勢です。ただし例外が2つ:

- **双対値が欲しいとき**は前処理が邪魔になるのでオフ(1-4)
- **presolveが時間を食いすぎる**超大規模ケースでは調整対象になる

## 数値の話:ソルバーは厳密には計算していない

MIPソルバーは浮動小数点で動いており、「ぴったり」は存在しません。実務で知っておくべき3点だけ:

### 1. トレランス(許容誤差)の存在

SCIPは既定で、制約違反 $10^{-6}$ 程度までを「実行可能」とみなします(`numerics/feastol`)。整数変数も $10^{-6}$ ずれまでは「整数」です。だからこの教材で繰り返してきた通り、**0/1変数の判定は `== 1` ではなく `> 0.5`** で書きます。

### 2. 巨大係数はトレランスを増幅する

$x \le 10^{9} y$ のような制約では、$y$ 側のわずかな誤差が $x$ 側で $10^9$ 倍に増幅されます。今回の小さな実験ではSCIPは正しく処理しました(presolveが限界を締めたため)が、大規模モデルで巨大係数と微小係数が混在すると、**「実行可能と報告された解が、検算すると制約を破っている」**事故が実際に起きます。目安として、**係数の範囲は $10^{-4}$〜$10^{6}$ 程度に収める**(単位を変える:円→千円、グラム→キログラム)のが安全圏です。Big-Mを絞る習慣(2-4)は、緩和だけでなく数値のためでもあります。

### 3. 目的関数に関係ない変数は「好き勝手な値」を取る

今回の実験で、$x \ge 40$ さえ満たせばよい問題の解が `x=50000` で返ってきました。バグではありません。$x$ が目的関数に入っていないので、**実行可能でありさえすればどんな値でも「最適」**なのです。解を業務に渡す前に、「動いてほしくない変数」には小さなコストを付けるか、後処理で正規化するのが実務の作法です。

## 「遅い」ときのチェックリスト(第4部のまとめ)

上から順に疑ってください。番号は関連する章です。

1. **ログを読む**(2-3)。gapはいくつか。primalが弱い(良い解が出ない)のか、dualが弱い(証明が進まない)のか
2. **LPギャップを測る**(4-1)。小規模データで50%超なら定式化の構造問題。Big-Mの緩み・集約リンクを探す(2-4, 3-4)
3. **対称性を疑う**(3-5)。同価な選択肢(同型の機械、無個性な箱)はないか。ログの symmetry 行を確認
4. **係数レンジを確認**。`writeProblem` で吐いて最大/最小係数を見る。$10^9$ が見えたら単位と M を見直す
5. **打ち切り設計に逃げる**(2-3)。業務が許すgapを決めて `limits/gap` を設定。「最適の証明」は本当に必要か?
6. それでも駄目なら**問題を分解する**——列生成(5-1)、Benders(5-4)、ヒューリスティクス併用(6-1)の出番

## まとめ

- 「手元では解けた」は保証にならない。**定式化の弱さは規模で顕在化する**(実測: F=15で不可視 → F=60で23倍差)。小規模でもLPギャップは測れる
- presolveは掃除人(変数184→150の実測)。きれいなモデルでは差が出ないのが正常。双対値が欲しいときはオフ
- トレランスと巨大係数の増幅を知る。**判定は `> 0.5`、係数レンジは $10^6$ まで、単位で調整**
- 目的に入らない変数の値は不定。業務に渡す前に正規化

これで第4部・強い定式化編は完了です。定式化の質を測り、強め、ソルバーの内部動作を読む道具が揃いました。
