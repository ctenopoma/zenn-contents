## Introduction

ここでは数学的な興味よりも**実務で使う技術**として最適化を扱います。定理の証明はしません。そのかわり、毎回必ず実例をひとつ置いて、コードを実行し、結果を図にして確かめます。

初回のこの記事でやることは2つです。

- 業務の困りごとを「**変数・制約・目的関数**」という3つの部品に翻訳する練習

数式はほぼ出てきません。コードは1本だけ出てきますが、読み飛ばしても大丈夫です(動かし方は次回やります)。

:::

## 「最適化っぽい仕事」は身の回りに転がっている

次のような相談は、どこの職場にもあります。

- 「アルバイト10人の**シフト表**、希望休を守りつつ公平に組みたい」
- 「トラック5台で30件配送する。**どの車がどこを回る**と総走行距離が短い?」
- 「限られた設備時間で、**どの製品を何個ずつ作る**と利益が最大?」
- 「広告予算1,000万円を**どの媒体にいくら**割り振る?」

これらは全部、人間がExcelと気合で「そこそこの答え」を作っている現場が多い仕事です。そして全部、数理最適化がそのまま適用できる形をしています。

共通点はこうです。

1. **決めたいことがある**(誰をいつ入れるか、何を何個作るか)
2. **守るべきルールがある**(希望休、設備時間、トラックの積載量)
3. **良し悪しの物差しがある**(公平さ、走行距離、利益)

この3つが揃った瞬間、その仕事は「数理最適化問題」として書けます。

## 3つの部品:変数・制約・目的関数

数理最適化の世界では、上の3つをこう呼びます。

| 部品 | 意味 | 例(シフト表なら) |
| ---- | ---- | ---- |
| **変数** | ソルバーに決めさせること | 「佐藤さんを月曜に入れるか?」(入れる=1 / 入れない=0) |
| **制約** | 破ってはいけないルール | 各日2人以上、希望休には入れない、週4日まで |
| **目的関数** | 解の良し悪しを測る1つの数値 | 出勤日数の最大と最小の差(=不公平さ)を最小に |

先ほどの4つの相談を、この3部品に翻訳してみます。

| 相談 | 変数 | 制約 | 目的関数 |
| ---- | ---- | ---- | ---- |
| シフト表 | 人×日の出勤(0/1) | 必要人数、希望休、連勤上限 | 不公平さ最小 |
| 配送ルート | 車×区間の通過(0/1) | 全件訪問、積載量 | 総走行距離最小 |
| 生産計画 | 製品ごとの生産量(数量) | 設備時間、材料在庫 | 利益最大 |
| 広告予算 | 媒体ごとの金額(金額) | 予算総額、媒体ごとの上限 | 獲得数最大 |

**翻訳さえできれば、「解く」のはソルバーの仕事です。** これがこの教材で一番伝えたいことです。解くアルゴリズムは教材の中盤でちゃんと扱いますが、実務の第一歩は「解く」ではなく「**書ける**」ことです。

## 問題クラスの地図

翻訳した問題は、変数と関数の性質で大きく4つに分類されます。この地図は今後全編を通して使うので、ここで一度眺めておいてください。

![問題クラスの地図](/images/mip-course-0-1-intro/fig1_map.png)

- 横軸: 変数が**連続**(生産量17.3kgのような小数OK)か、**整数**を含む(人は0.5人にできない)か
- 縦軸: 制約・目的関数が**線形**(足し算と定数倍だけ)か、**非線形**か

この教材が歩くのは赤い矢印のルートです。

- **線形計画(LP)**: 連続×線形。最適化の出発点で、簡単な数学(連立一次方程式と不等式)で理解できます。第1部で扱います
- **混合整数計画(MIP)**: 整数変数が入った瞬間、問題は質的に難しくなります。そのかわりシフト・配送・ON/OFFのような実務の大半がここに入ります。第2部以降の主戦場です
- 非線形の世界(NLP/MINLP)は、この教材では深入りしません。ただし「非線形な現実を線形+整数変数で近似する」技は第2部で扱います。実務ではこの技のほうが出番が多いからです

## 体験:シフト表をSCIPに作らせる

言葉だけだと嘘くさいので、実際にやってみます。題材は5人×1週間のミニシフト。

- 平日は2人、土日は3人必要(計16枠)
- 希望休が5件ある(佐藤さんは週末NG、など)
- 全員週4日まで
- **出勤日数の差(最大−最小)をなるべく小さく**して公平にしたい

これをPySCIPOptで書くと、本質部分は20行ほどです。

```python
from pyscipopt import Model, quicksum

staff = ["佐藤", "鈴木", "高橋", "田中", "伊藤"]
days = ["月", "火", "水", "木", "金", "土", "日"]
need = {"月": 2, "火": 2, "水": 2, "木": 2, "金": 2, "土": 3, "日": 3}
ng = {("佐藤", "土"), ("佐藤", "日"),        # 佐藤さんは週末NG
      ("鈴木", "水"), ("田中", "月"), ("伊藤", "金")}

m = Model("mini-shift")
# 変数: xを1にする=その人をその日に入れる
x = {(s, d): m.addVar(vtype="B", name=f"x_{s}_{d}") for s in staff for d in days}

# 制約
for d in days:                                   # 各日、必要人数ちょうど
    m.addCons(quicksum(x[s, d] for s in staff) == need[d])
for s in staff:                                  # 各人、週4日まで
    m.addCons(quicksum(x[s, d] for d in days) <= 4)
for s, d in ng:                                  # 希望休は割り当てない
    m.addCons(x[s, d] == 0)

# 目的関数: 出勤日数の最大と最小の差(不公平さ)を最小化
mx, mn = m.addVar("max"), m.addVar("min")
for s in staff:
    total = quicksum(x[s, d] for d in days)
    m.addCons(total <= mx)
    m.addCons(total >= mn)
m.setObjective(mx - mn, "minimize")

m.optimize()
```

コードの意味が全部わからなくても今は問題ありません。「変数を作る」「制約を足す」「目的関数を決める」という3部品がそのまま関数名になっていること(`addVar` / `addCons` / `setObjective`)だけ見てください。

実行結果はこうなりました。

```text

出勤日数の差: 1
佐藤: ・ ● ● ・ ● ・ ・  (3日)
鈴木: ・ ・ ・ ● ・ ● ●  (3日)
高橋: ● ・ ・ ・ ・ ● ●  (3日)
```

## 「解けた」の中身:optimal という一言の重み

出力の1行目に `状態: optimal` とありました。これは「良さそうな答えが出た」ではありません。

**「出勤日数の差が1のシフト表を見つけた。そして、差が0のシフト表はこの条件下では存在しない。」**

という**証明付きの宣言**です(実際、枠は全部で16、人は5人なので、16÷5は割り切れず全員同じ日数にはできません。ソルバーはこれを自力で見抜いています)。

:::message
`optimal` はSCIPが返す終了ステータスのひとつです。ほかにも `infeasible`(条件を全部満たす表は存在しない)、`unbounded`、`timelimit`(制限時間切れ。解はあるが最適とは限らない)、`gaplimit`、`unknown` などがあります。実務では `optimal` かどうかで後続処理を分けるので、`m.getStatus()` の値は必ず確認してください(第2部でログと合わせて詳しく扱います)。

- 一覧と定義: [SCIP Doxygen — `type_stat.h`(`SCIP_Status` enum)](https://www.scipopt.org/doc/html/type__stat_8h.php)
- Python側のAPI: [PySCIPOpt Model API — `getStatus()`](https://pyscipopt.readthedocs.io/en/latest/api/model.html)
:::

人間が気合で作ったシフト表との違いはここです。気合の表は「これより良い表があるかも」という不安が消えません。最適化の答えは「**これ以上は無い**」まで込みで返ってきます。この「最適性の証明」が何をしているのかは、第2部の分枝限定法の回で種明かしします。

ただし実務では、証明が終わるまで待てない規模の問題もたくさんあります。「厳密な最適は無理でも、良い解を速く」という戦い方(これも教材の後半で扱います)を含めて、**どこまでが保証できて、どこからが妥協なのかを自分で判断できる**ようになるのがこの教材のゴールです。

## なぜソルバーはSCIPなのか

この教材では全編を通してソルバーに **SCIP**、モデリングに **PySCIPOpt** を使います。理由は3つです。

- **非商用なら無償で、実務水準の性能がある** 学習からPoC、(ライセンス条件を満たせば)本番まで同じ環境で行けます
- **中身に手が入る** 教材の後半で、分枝のルールや列の生成(プライサー)をSCIPに自作プラグインとして差し込みます。ブラックボックスな商用ソルバーではカスタムが困難です
- **ログが饒舌** ソルバーが今なにをしているかが読み取れるので、教材として都合が良い

**商用ソルバー**(Gurobi、Knitro など)を使う現場でも、モデリングの考え方はそのまま通用します。
