シフトスケジューリングは、おそらく**日本で一番多く発生している最適化ニーズ**です。そして実務に投入した途端、必ずこの事件が起きます。

> ソルバー「**infeasible**(実行不能)」
> あなた「……で、どこを直せばいいの?」

ソルバーは「無理です」としか言いません。今回はシフト問題の定式化パターン一式に加えて、この**実行不能との付き合い方**——原因の特定と、ソフト制約による柔らかい設計——を実測でやります。

:::message
コードと数値はすべて手元で実行した実測です。
:::

## 題材:コールセンターの週次シフト

- スタッフ8名、1週間、シフトは**早番/遅番**の2種
- 必要人数: 平日は早3・遅2、土日は早2・遅2(計33枠)
- 希望休10件(**金曜に6件集中**——後で効いてきます)
- 1人週5日まで、**遅番の翌日に早番は禁止**(休息ルール)
- なるべく公平に(出勤日数の最大−最小を小さく)

## 定式化パターン一式

変数は「誰が・何曜日に・どのシフトか」の3添字バイナリと、補助の「出勤したか」です。

```python
x = {(s,d,t): m.addVar(vtype="B") for s in staff for d in days for t in shifts}
work = {(s,d): m.addVar(vtype="B") for s in staff for d in days}
```

シフト問題の制約は、だいたい次の4種類に分類できます。

```python
# (1) リンク制約: 1日1シフトまで(work = その日のシフト数の和)
m.addCons(work[s,d] == quicksum(x[s,d,t] for t in shifts))

# (2) カバー制約: 各枠の必要人数
m.addCons(quicksum(x[s,d,t] for s in staff) >= need[d,t])

# (3) 個人の稼働制約: 週5日まで、希望休
m.addCons(quicksum(work[s,d] for d in days) <= 5)
m.addCons(work[s,d] == 0)          # (s,d)が希望休のとき

# (4) 連続性の制約: 遅番→翌日早番の禁止
m.addCons(x[s, days[i], "遅"] + x[s, days[i+1], "早"] <= 1)
```

(4)は前々回のパターン集の「排他」そのものです。「連勤は5日まで」のような窓制約も `quicksum(work[s, days[i:i+6]]) <= 5` と同じ発想で書けます。公平性は1-5までに使った最大−最小の形です。

## 事件発生:infeasible

これをそのまま解くと:

```text
ハード制約のみ: infeasible
```

ソルバーが返すのはこの一言だけです。解はもちろん、「どの制約が悪いか」も教えてくれません。しかも困ったことに、**原因は1つの制約ではなく制約の組み合わせ**です(希望休だけなら守れる、必要人数だけなら守れる、両方同時が無理)。

## 診断法:スラック変数で「どこがどれだけ無理か」を測る

実務で一番使える診断法は、**破ってもよい制約に「違反量」の変数(スラック)を付けて、違反の合計を最小化する**ことです。カバー制約をこう書き換えます。

```python
short[d,t] = m.addVar(lb=0)   # 不足人数(スラック)
m.addCons(quicksum(x[s,d,t] for s in staff) + short[d,t] >= need[d,t])

# 目的関数: 不足への重いペナルティ + 公平性
m.setObjective(100 * quicksum(short.values()) + (mx - mn), "minimize")
```

解けるようになったうえで、**スラックが正になった場所=無理の在り処**が数値で出てきます。

```text
ソフト版: optimal  目的値: 300.0
不足箇所:
  金曜早番: 3人不足 (必要3人)
```

![カバー状況](/images/mip-course-3-2-shift/fig2_cover.png)

一目瞭然です。**金曜に希望休が6件集中**し、出勤できるのは木村・黒田の2名だけ。金曜の必要5人(早3遅2)に対して3人分がどうしても埋まりません。ソルバーはその2名を遅番に充て、早番を空ける形で「最も傷の浅い破り方」を選びました。

これで会話が変わります。「実行不能でした」ではなく——

> 「**金曜だけ3人足りません。** 希望休6件のうち1〜2件を調整いただくか、金曜の必要人数を見直すか、どちらにしますか?」

意思決定の材料を持って現場と話せる。これがスラック診断の価値です。

:::message
この「全ハード制約にスラックを付けて違反最小化」は**弾性化(elastic relaxation)**と呼ばれる定石です。類似の道具に、矛盾する制約の極小集合を特定する**IIS(Irreducible Infeasible Subsystem)**がありますが、シフトのような問題では弾性化のほうが「何人分無理か」という**量の情報**まで出るぶん実務向きです。
:::

## できあがったシフト表

![シフト表](/images/mip-course-3-2-shift/fig1_shift.png)

チェックポイント:

- 赤い「休」(希望休)は全件守られている
- 遅番の翌日に早番が入っている人はいない
- 出勤日数は**全員ぴったり4日**(公平性の目的関数が効いた)

ひとつ面白い現象があります。カバー状況の図をよく見ると、**土曜早番に4人**入っています(必要は2人)。カバー制約を `>=` で書いたので余剰配置は自由であり、ソルバーは「全員4日」の公平性を成立させるために余った稼働を土曜に置いたのです。**モデルは書いたことしか守らない**(1-2)の再演です。余剰人件費が困るなら、余剰にも小さなペナルティを付けるか `==` にします。

## ペナルティ設計の作法

ソフト制約化で必ず聞かれるのが「**重みはいくつにすればいいの?**」です。定石を3つ。

1. **優先度に桁差をつける**。今回は不足1人=100、公平性の差1日=1。「人数不足は公平性の100倍嫌だ」という業務判断の直訳です。桁が近いと、ソルバーが「不足1人と引き換えに公平性を50改善」のような**意図しない取引**をします
2. **絶対に破れないものはハードのまま残す**(法規制の休息時間など)。何でもソフトにすると「罰金を払えば法律を破れる」モデルになります
3. **ペナルティの内訳を必ず報告する**。目的値300という数字ではなく「不足3人分」と翻訳して現場に見せる。今回の図2がその実例です

うまく設計されたシフトモデルは、実行不能を出さずに「**守れた/守れなかった一覧**」を毎回出力する運用になります。ソルバーとの喧嘩(infeasible)を、現場との対話の材料に変換する——これがソフト制約設計の本質です。

## まとめ

- シフトの制約は4分類:**リンク・カバー・個人稼働・連続性**。全部これまでのパターンの組み合わせ
- infeasibleは情報ゼロ。**スラック付きで解き直して「どこが何人分無理か」を測る**(弾性化)
- ペナルティは桁で優先度を表現。法規制はハードのまま。内訳を現場語で報告
- `>=` の余剰配置に注意(実測で土曜に余剰4人が出た)

## 次回

次回は**巡回セールスマン問題(TSP)**。配送ルート最適化の核であると同時に、「**制約が指数個あって全部は書けない**」問題の代表です。必要になった制約だけ後から足す**遅延制約生成**と、SCIPのコールバック機能に初めて触れます。列生成法(変数を後から足す)の鏡写しになる重要回です。
