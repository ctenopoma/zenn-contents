## この記事について

数理最適化を大学1年レベルから列生成法・分枝価格法まで学ぶ教材、第2部・MIP基礎編の3本目です。目次はこちら。

@[card](https://zenn.dev/ctenopoma/articles/mip-curriculum-toc)

MIPが「一瞬で解ける」時期を過ぎると、エンジニアの仕事の多くは**ソルバーのログを読むこと**になります。ログが読めると、

- 「あと1分待つべきか、もう打ち切ってよいか」を根拠を持って判断できる
- 「モデルが悪いのか、単に問題が難しいのか」の切り分けができる

前回、分枝限定法の上界・下界・ギャップを手作りの探索木で見ました。今回は本物のSCIPのログの中でそれらを読みます。

:::message
コードとログはすべて手元で実行した実物です。題材は多次元ナップサック問題(品物120個、容量制約15本)。頑張っても60秒では最適性を証明しきれない、ほどよく嫌な問題です。
:::

## 準備:ログを保存しながら解く

```python
m = Model("mkp")
# ...(定式化)...
m.setParam("limits/time", 60)   # 60秒で打ち切り
m.setLogfile("scip.log")        # ログをファイルにも保存
m.optimize()
```

`hideOutput()` を呼ばなければログはコンソールに流れます。`setLogfile` で保存しておくと、後からの解析(この記事の最後でやります)に使えます。

## ログ前半:presolve(前処理)

最初に流れるのは前処理の報告です。

```text
presolving:
(round 1, exhaustive) 0 del vars, 0 del conss, ... 15 upgd conss, ...
   (0.0s) probing: 51/120 (42.5%) - 0 fixings, ...
   (0.0s) no symmetry present (symcode time: 0.00)
presolved problem has 120 variables (120 bin, 0 int, 0 cont) and 15 constraints
     15 constraints of type <knapsack>
```

読みどころ:

- **del vars / del conss**: 前処理で消せた変数・制約の数。ここが大きい場合、モデルに冗長がある(悪いことではない。ソルバーが掃除してくれた)
- **upgd conss**: 一般の線形制約が、より構造の強い制約型(ここでは`knapsack`)に**格上げ**された。SCIPは制約の型ごとに専用の攻め方を持っているので、格上げは歓迎すべき知らせ
- **presolved problem has ...**: 前処理後の問題サイズ。**ソルバーが実際に戦う問題はこちら**です

## ログ中盤:メインテーブル

ここからが本体です(実ログの抜粋)。

```text
 time | node  | left  |LP iter| ... |cuts | ... |  dualbound   | primalbound  |  gap
p 0.0s|     1 |     0 |     0 | ... |   0 | ... | 8.136000e+03 | 2.449000e+03 | 232.22%
  0.0s|     1 |     0 |    85 | ... |   0 | ... | 3.209257e+03 | 2.449000e+03 |  31.04%
r 0.0s|     1 |     0 |    85 | ... |   0 | ... | 3.209257e+03 | 3.130000e+03 |   2.53%
  0.0s|     1 |     0 |    91 | ... |   1 | ... | 3.207973e+03 | 3.130000e+03 |   2.49%
r 0.0s|     1 |     0 |    91 | ... |   1 | ... | 3.207973e+03 | 3.138000e+03 |   2.23%
L 0.2s|     1 |     0 |   358 | ... |  14 | ... | 3.205834e+03 | 3.161000e+03 |   1.42%
 59.9s|116300 | 49532 |957775 | ... |3436 | ... | 3.191845e+03 | 3.172000e+03 |   0.63%
```

### 最重要の3列

| 列 | 意味 | 前回の言葉で |
| ---- | ---- | ---- |
| **primalbound** | 見つかっている最良の整数解の値 | **下界**(最低これは取れる) |
| **dualbound** | 未探索の枝も含めた理論上の天井 | **上界**(これ以上は無い) |
| **gap** | 両者の相対差 | 残っている改善余地の**保証値** |

### 行頭の1文字:誰が解を見つけたか

行頭にときどき付く文字は「**この行でprimalboundを更新した犯人**」です。

- `p`: presolve中の自明なヒューリスティクス(とりあえず全部0、など)
- `r`: 丸め系ヒューリスティクス(LP解を上手に丸める——2-1で「丸めは保証がない」と言いましたが、**保証なしでよければ**有力な解の源です)
- `L`: 大規模近傍探索系(RENSなど。第6部の主役)
- `*`: 分枝の末端で整数解に到達(木の探索そのものの成果)

上のログでは、最初の0.2秒に `p → r → r → L` と畳みかけて、gapを232%から1.42%まで一気に潰しています。**現代のソルバーの解は、その多くを木の探索ではなくヒューリスティクスが見つけている**ことがログから読み取れます。

### その他の主要列

- **node / left**: 処理済みノード数と未処理ノード数。`left` が伸び続ける間は木が広がり続けている(=まだ地力の勝負)
- **LP iter**: 単体法の累計反復回数(1-3で見たピボットの回数)。1ノードあたりのLP反復(`LP it/n`)が大きいとLPが重い
- **cuts**: 追加された切除平面の枚数(第4部で扱います)。根ノードでcutsが増えるたびにdualboundがじわじわ下がっているのが上のログでも見えます

## ログ終盤:サマリ

```text
SCIP Status        : solving was interrupted [time limit reached]
Solving Time (sec) : 60.00
Solving Nodes      : 116503
Primal Bound       : +3.17200000000000e+03 (846 solutions)
Dual Bound         : +3.19184344472954e+03
Gap                : 0.63 %
```

60秒で11.6万ノードを処理し、整数解を**846個**見つけ、最良は3172。天井は3191.8。したがって「**3172という解を持っている。真の最適が何であれ、3172との差は最大0.63%**」という保証付きの状態で時間切れになりました。

この0.63%を「十分」と見るかどうかは、あなたのビジネス次第です。判断材料はログが全部くれています。

## 可視化:boundの推移を描く

ログをパースして、primalboundとdualboundの推移をグラフにしました(パース用の正規表現はログの行頭形式 `文字? 時間s|...` に合わせるだけです)。

![収束グラフ](/images/mip-course-2-3-scip-log/fig1_convergence.png)

- **左(全体)**: 最初の1秒でgapの大半が潰れ、残り59秒は上界がミリ単位で下がるだけ。**MIPの計算時間の大半は「最後のわずかなgapの証明」に費やされる**——極めて典型的なパターンです
- **右(最初の1秒)**: ヒューリスティクス群(`r`, `L` の行)が階段状に解を改善していく様子

この形を覚えておいてください。「解はすぐ良くなる、証明は遅い」。だから実務では**打ち切り方**が設計項目になります。

## 実務の設定:打ち切りの3点セット

```python
m.setParam("limits/time", 600)     # 時間制限 [秒]
m.setParam("limits/gap", 0.01)     # gap 1% 以下になったら終了
m.setParam("limits/solutions", 5)  # 解が5個見つかったら終了(使いどころは限定的)
```

効果を実測しました。60秒粘った場合と、gap許容1%で打ち切った場合の比較です。

| 設定 | 計算時間 | 得られた解 | 保証 |
| ---- | ---- | ---- | ---- |
| 時間制限60秒 | 60秒 | 3172 | gap 0.63% |
| **gap許容1%** | **5.1秒** | 3169 | gap 0.96% |

**12分の1の時間で、価値にして0.1%しか違わない解**が手に入りました。「1%以内なら文句なし」という業務なら、gap許容を1%にセットするだけで日次バッチが12倍速くなる、という話です。

推奨の型:

- **バッチ処理**: `limits/time` と `limits/gap` を両方セット(先に達した方で停止)。gapは業務が許す値に
- **対話的な検討**: まず `limits/time = 30` で小さく回して感触を掴む
- 終了後は必ず `getStatus()` を確認(`optimal` / `timelimit` / `gaplimit` で後続処理を分ける)。`getGap()` で保証値を記録に残す

## トラブルの読み分け早見表

| ログの症状 | 疑うべきこと | 次の一手 |
| ---- | ---- | ---- |
| primalboundが長時間 `--`(解が1つも無い) | 実行不能に近いモデル/ヒューリスティクスが効かない構造 | 制約を緩めて実行可能性を確認(3-2でIISをやります) |
| dualboundが全く動かない | LP緩和が弱すぎる(丸めの余地が大きすぎる) | 定式化の強化(第4部) |
| gapが小さいのに終わらない | 「証明の遅さ」问题。実害は小さい | gap許容で打ち切る |
| `left` が数十万で伸び続ける | 木が爆発。モデルの対称性を疑う | 対称性除去(3-5, 4-3) |

## まとめ

- ログの主役は **primalbound(手持ちの解)/ dualbound(天井)/ gap(残る改善余地の保証)**
- 行頭の文字で「解を見つけた犯人」がわかる。多くはヒューリスティクスの手柄
- 「解はすぐ良くなる、証明は遅い」——だから `limits/gap` での打ち切りが実務の武器になる(実測: 時間1/12で価値差0.1%)
- 終了後は `getStatus()` と `getGap()` をコードで確認・記録する
