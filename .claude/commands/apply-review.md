argument-hint: <記事のslug>（省略時は未反映のものすべて）

iPad で手書き添削した PDF を読み取り、`articles/<slug>.md` に反映する。

対象: $ARGUMENTS

手順:

1. `git pull origin <現在のブランチ>` で iPad から push された添削 PDF を取り込む。
2. `node tools/review/pending.mjs $ARGUMENTS` を実行する。
   未反映の添削 PDF がページ画像に展開され、パスが表示される。
3. 表示された PNG を **1 ページずつ全部** Read する。読み飛ばさない。
   併せて `review/<slug>/blocks.json` と `articles/<slug>.md` を読む。
4. 手書きの読み取りと対応付け:
   - 右の余白のコメントは、**同じ高さにある ¶N のブロック**への指示。
   - コメント頭に `¶12` と書いてあればそれが優先。
   - `blocks.json` の `startLine`/`endLine` が Markdown 上の該当行。`preview` で本文と突き合わせて確認する。
   - 記号の目安: 取り消し線=削除 / `∧`=ここに追加 / `?`=意味が不明 / `◯`=良い(残す) / `→`=書き換え案
5. **読み取り結果を先に一覧で提示する**。修正を当てる前に、次の形式で列挙すること:
   `¶12 (L88-L94) | 読み取った指示 | どう直すか`
   - 判読できなかった手書きは推測で埋めず、`【判読不能】` として一覧に残し、後でまとめて聞く。
   - 「この段落まるごと書き直し」のような裁量の大きい指示は、直す前に方針を一言確認する。
6. 一覧に沿って `articles/<slug>.md` を Edit で修正する。
   - 指示された箇所以外は触らない。ついでのリファクタや表現の統一は勝手にやらない。
   - 数値・実測値の書き換えを指示された場合、根拠が本文/コードにないなら勝手に書かず質問する。
7. `node tools/review/record-applied.mjs <添削PDFのパス> "<反映内容の要約>"` で台帳に記録する。
   （これを飛ばすと次回また同じ添削を読み直すことになる）
8. コミットして push する。メッセージは `<slug>: 添削反映（¶12,¶20,¶31）` のように、当てたブロックを列挙する。
9. 最後に、判読不能だった箇所と、確認が要る箇所だけを簡潔に報告する。

注意:
- 添削 PDF の表紙にある commit と現在の `articles/<slug>.md` がズレている場合、
  ¶N と行番号の対応が崩れている可能性がある。その場合は `preview` の文面で照合し、
  一致しないブロックは機械的に当てず報告する。
- 手書きは誤読しうる。確信が持てない指示は当てるより聞く。
